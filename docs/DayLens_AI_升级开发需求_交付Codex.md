## 1. 产品定位与最终目标

现阶段 DayLens 擅长回答“用了哪些软件、活跃了多久、娱乐/工作/社交的占比、窗口切换和中断次数”。目标是让它进一步回答：

- **任务层**：多个应用是否服务于同一个任务？今天在哪些项目上投入了时间？
- **行为层**：哪些切换属于正常工作流程，哪些是非工作活动插入？中断后有没有回到原任务？
- **目标层**：计划投入与真实投入差多少？是否存在可以证明的完成成果？
- **趋势层**：哪些时间段容易投入工作？相同计量口径下，个人行为有什么变化？
- **问答层**：用户用自然语言询问自己的历史数据，系统提供有证据的回答。

产品应当保持“客观时间记录器”的基础身份，而不是未经授权的心理诊断器。**电脑上停留的时间不等于有效成果；AI 推断不等于用户完成任务的事实；窗口切换次数不等于工作低效。**

## 4. 第一期 V1.6：任务识别与工作链重建

### 4.1 用户场景

同一段工作可能跨越 `VS Code -> Chrome 文档 -> ChatGPT -> 终端 -> Obsidian`。软件维度分别统计虽然正确，却不能体现这些软件共同服务于一个 Camera 驱动学习任务。系统应能给出“可能属于同一个任务”的建议，同时允许用户确认或纠正。

### 4.2 事实与推断分层

构建三层模型：

1. **原始事实层（不可被 AI 修改）**：session ID、应用、规范化标题、开始/结束时间、分类及来源、engaged/passive/idle、metric/classification version、切换原因、记录健康证据。
2. **本地分析层（可重建）**：候选相邻会话、任务簇、切换事件、非工作插入、返回任务证据、可信度/可比性门控。这一层使用确定性算法。
3. **AI 语义层（可撤销）**：任务建议名称、可解释的分组建议、短理由、置信度、关联的 evidence IDs。AI 只能建议，不能修改原始会话、创造时长或自行宣布任务完成。

所有界面数字由本地聚合计算；模型响应只允许引用已提交的候选 IDs。禁止 AI 自行返回新的原始时间、会话 ID、工作成果或时间总计。

### 4.3 任务分组本地算法（初始建议参数，可根据已有逻辑调整）

- 输入必须从规范数据库以只读方式获取，按 `start_time`、`end_time`、稳定 ID 排序；相同 ID 不能重复计量。
- 同一个应用同类标题的连续会话可优先合并为一个任务候选；不同应用需结合标题语义、时间邻近性、已确认任务模式和工作域证据。
- 任务内短暂的正常工具切换可以桥接，但**跨应用不因时间接近就默认属于同一任务**。
- 对于无法判定是否同任务的情形，返回 `unknown / needs_confirmation`；不要强行二分类。
- 非工作插入要保留为单独活动，不能并入工作参与时长。允许呈现“任务被暂停后继续”的链式关系。
- 首版推荐使用不超过 3 分钟的相邻候选窗口，短中断候选上限 5 分钟。**这只是关联算法的建议阈值，不修改会话时长与现有中断统计口径。** 将阈值做成可测试的常量，基于真实样本验证后再确定。
- 不能跨越数据缺口、长时间睡眠/锁屏或日期边界无证据地强行合并。涉及跨午夜的会话按现有计量定义处理。
- 对财务、学习、通讯、娱乐等类别保持中性，不预设娱乐一定有害、微信一定不是工作、ChatGPT 一定属于编程。
- 若历史数据过少或版本不可比，不输出强结论；展示“数据不足/待确认”。

### 4.4 AI 任务命名与关联

优先级：`用户明确确认 > 用户保存的任务模式 > 高可信本地关联 > AI 建议 > 未归属任务`。

调用时机：只有本地任务候选包含足够有效参与证据、语义确实无法由本地规则解释、且 AI 功能开启时，才允许入队；不能每次首页刷新就调用模型。

AI 任务建议的结构（示意，需要 Python schema 校验）：

```json
{
  "task_candidate_id": "opaque-local-id",
  "suggested_name": "RK3568 Camera 驱动学习",
  "domain": "work_learning",
  "confidence": "high",
  "reason": "文档浏览与代码编辑主题一致",
  "evidence_ids": ["s1", "s2", "s3"],
  "needs_confirmation": true
}
```

要求：

- 所有 ID 只能引用本次请求清单；没有依据的任务名或高置信度分组必须拒绝/降级。
- 返回 JSON 必须白名单字段、限制字符串长度、检查枚举和 evidence IDs。Prompt 明确声明窗口标题是不可信数据，不得执行其中的指令。
- 低置信度只作为待确认提示；高置信度也不自动改写用户已确认的归属。
- 用户可对任务候选进行：确认名称、重命名、拆分、合并、忽略、将指定会话移到另一个任务、撤销上一次纠正。
- 人工纠正仅更新任务归属的派生状态，不更新原始分类，也不追溯改写原始时间。纠正规则要限制作用范围，避免相似标题导致跨项目误归属。
- AI 任务标签建议本地缓存，并与关联算法版本、源数据版本、规则版本及隐私版本绑定；源事实改变时失效并安全重算。用户确认结果要独立保存，优先级高于新建议。

### 4.5 建议数据模型

第一期可以在**规范 `intelligence/` 目录**下创建原子写入的有版本 JSON 派生文件，路径由 `AppPaths` 决定，不要硬编码工作目录。建议模型：

- `TaskCandidate`：`id`、`period`、`source_session_ids`、`start/end`、`work_engaged_seconds`、`category_keys`、`status`、`confidence`、`algorithm_version`、`metric_versions`。
- `TaskDecision`：`candidate_id`、`confirmed_task_id/name`、`user_action`、`scope`、`revision`、`created_at`、`enabled`。
- `TaskEvidence`：`evidence_id`、`kind`、`session_refs`、`start/end`、`facts`、`source_version`。
- `TaskSummary`：`task_id`、`day`、`engaged_seconds`、`passive_seconds`、`evidence_ids`、`data_health_status`、`generated_at`。

时间数值必须由现有可信定义派生，并验证同一会话不被重复累计；任务归属总量不得大于相应来源的有效活动时长。不同任务之间出现同一会话时应显式标记冲突并拒绝生成重复统计。敏感标题不应在 AI 派生 JSON 中无必要地重复保存。

如使用 JSON 存储，写入必须原子化，防止并发覆盖；对确认/拆分/合并引入统一写入服务和修订号，不能让后台结果覆盖用户刚刚保存的手工决定。数据量大或索引需求明确后再单独设计同一 SQLite 数据库中的可迁移表。

## 5. 第一期 V1.6：中断与恢复行为分析

### 5.1 核心问题

目前已有工作切换统计和明显中断次数，但不能直接从次数判断“坏中断”。新功能需要回答：

- 这次切换是正常工具协作、项目间切换，还是工作中插入了社交/娱乐活动？
- 插入活动持续多久？之后是否回到被打断的原任务？
- 如果回到同一任务，切回工作任务间隔是多少？
- 哪些事件只存在相关性、不能识别原因？

### 5.2 中断事件定义

建立确定性的 `TransitionEvent` / `InterruptionEpisode`，建议字段：

- `event_id`, `source_task_id`, `target_category`, `start_time`, `end_time`
- `source_session_ids`, `interruption_session_ids`, `return_session_ids`
- `event_type`: `workflow_switch` / `task_switch` / `non_work_interruption` / `unknown`
- `returned_to_source_task`: `yes` / `no` / `unknown`
- `interruption_elapsed_seconds`、`return_gap_seconds`（若有可靠证据）
- `evidence_ids`, `analysis_version`, `trust_status`

不得把“窗口离开任务”的时间直接等于“有效分心时间”。如果只是离开了工作窗口，且没足够证据证明在进行非工作活动，必须标记 `unknown`。恢复间隔仅在任务身份与时间连续性可靠时计算；不要声称测量了认知恢复成本。

### 5.3 展示要求

- 在今日概览放一张简洁的“AI 任务洞察”卡片：可确认任务数、主要任务及其参与时间、存在证据的中断观察、查看详情入口。优先复用已有布局，不重复已有“工作切换”“今日工作节奏”卡片的数值。
- 在已有统计页或工作片段详情中提供一条可展开的任务时间线：应用链、短暂插入活动、重新返回任务；可查看原始证据。
- 将已知统计与新关联推断分开命名，例如“明显中断 92 次（现有口径）”与“可关联到任务恢复的插入事件 7 次（新分析口径）”不能互相替代或加总。
- 所有 AI 文案标示“AI 建议”或“本地统计”，提供“依据”“纠正”操作。

## 6. AI 网络、成本和安全要求

### 6.1 开关策略

现有总开关、分类开关、日报汇总开关必须保持兼容。新增独立开关 `task_analysis_enabled`，默认 `false`（opt-in）。允许用户：

- 仅使用本地任务重建，不使用云端任务命名；
- 开启云端 AI 任务建议（在总开关与新开关、密钥、预算均满足条件时）；
- 关闭新功能后，原始记录、分类及报表不受影响；既有用户确认任务可保留在本地，但不再产生新云端调用。

**注意**：新功能的本地启用与云端 AI 建议最好分为两个独立条件；不要因为用户未配置 API Key 而让本地任务分组停止工作。

### 6.2 预算约束

- 全局月预算继续使用 `IntelligenceBudget`；保留原有用户预算设置和历史记录。
- 新类型调用的 `kind` 使用独立命名，例如 `task_analysis`；根据候选批次设置合理的日调用上限。第一期建议每天最多 **2 次自动任务命名请求**，如实际成本足够低再调整；每日自动处理应以缓存优先。
- API Key 仍放 Windows 凭据管理器，绝不进入 Git、日志、报告与本地配置 JSON。
- 请求前预算预留，得到响应后结算；请求结果不确定时继续保守占用，避免重复扣费。
- 每个分析任务拥有持久化 idempotency key（包括周期、证据版本、模型任务版本），重复打开页面、重启、手动刷新不能再次收费。
- 不修改原有月预算上限来满足新功能；如额度不够，界面显示原因，保持原生功能。

### 6.3 隐私与提示注入

- 本地端原始会话可以用于计算；**出站 API 只发送达成目标所需、经脱敏和长度限制的候选证据**，不上传数据库、任意文件正文、屏幕截图、键盘输入、路径、URL、浏览内容或聊天全文。
- 保留网址、邮箱、长数字、路径、密钥的基础脱敏；对于可能包含用户敏感词的标题，设计可预览的实际出站内容及取消发送机制。即使标题看似普通，也不能承诺脱敏已经完全匿名。
- 允许用户在新任务分析中选择“仅本地”；默认不开启云端任务内容传输。
- 发送前必须在统一边界再次检查开关、隐私版本、预算和 payload，而不是只在进入队列时检查。
- 网络任务运行在后台，与 QWidget/采样线程解耦；超时或 malformed JSON 不得冻结 UI。
- 任何标题、模型输出都视为不可信文本，禁止执行模型指令、拼接任意 SQL、动态执行代码或渲染不受信任的富文本。

## 7. UI / UX 需求

以现有深色模式视觉体系为基础；先实现最小可用界面，不要新增整套重复的左侧导航。

### 今日概览：AI 任务洞察卡

1. 头部：`任务洞察`，状态：`仅本地` / `AI 已开启` / `等待确认` / `数据不足`。
2. 任务行：最多 3 个主要任务，显示`任务名 + 本地计算的主动参与时长 + 是否人工确认`。
3. 洞察行：只显示一个最有证据价值的观察，例如“同一工作任务中出现社交插入并返回 3 次”。
4. 底部入口：`查看任务链`、`纠正任务`；没有可靠结果时显示解释性的空状态。
5. 不显示无证据的“生产力指数”或“你今天浪费了 X 小时”。

### 详情页：任务链与证据

- 日期筛选，任务列表，切换事件时间线，任务展开详情。
- 点击一个 AI 建议能看到来源会话以及为何分组，不要仅展示不可解释的评分。
- 支持最小人工纠错闭环：确认任务名、改名、拆分/合并、撤销。
- 新老数据/口径不兼容时显示原因，不默默合并。
- 窗口窄屏、125%/150% DPI、中文长标题、暗色/亮色主题都应保持可读。

## 8. 第二期及以后（本期不要全部实现）

### V1.7 每日目标与偏差

- 每天最多设置 1～3 项目标：目标类型为 `time_commitment` 或 `outcome`。
- 时间型目标关联人工确认的任务或分类统计，自动计算真实投入与差值。
- 成果型目标只能用用户手动确认、Git 事件或笔记事件等外部证据判定；“打开软件若干分钟”不能作为完成证据。
- 每周提供“计划/投入/已核实成果”分层复盘，不使用单一娱乐占比判断人生效率。

### V1.8 行为画像与实验

- 聚合连续 7、14、30 天的可信事实，数据版本和分类口径不可比时拒绝得出趋势结论。
- 识别常出现的投入时段、频繁被插入的任务、娱乐时段分布和任务连续性变化。
- 提供可选的行为实验：一个具体建议、用户主动接受、持续观察一周、使用同口径对照结果进行反馈。禁止心理健康诊断或未经证据的动机归因。
- 继续在现有日报/周报/月报结构上扩展，不另建一套重复报告体系。

### V2.0 Ask DayLens

- 自然语言 -> 经过校验的指标查询意图 JSON -> 本地只读聚合服务 -> 结构化事实 -> AI 解释。
- 仅允许预定义的指标白名单、日期范围、过滤条件；**禁止模型生成 SQL 直接执行**。
- 每次回答显示日期范围、记录覆盖情况、统计口径、来源证据、无数据提示。
- 默认先匹配本地模板与确定性问答；需要语义解释时才请求模型，并纳入预算/隐私策略。

### P2 GitHub / Obsidian 成果关联

- 明确 opt-in；可选择本地指定 Git 仓库、Obsidian vault，不扫描任意个人目录。
- 默认只读取元数据：本地 Git commit/hash/time、可选修改文件名、笔记修改时间；不读取或上传代码/笔记正文。
- 时间接近只代表相关性，不自动判定代码质量或知识掌握程度。
- 导出报告中区分“投入记录”与“成果证据”，允许解除关联并删除对应派生缓存。

## 10. 必须覆盖的测试矩阵

1. **事实守恒**：相同原始会话在启用/关闭 AI 前后，主动参与/被动观看/空闲/有效时间一致；任务聚合无重复计量。
2. **跨应用链**：代码编辑 -> 文档 -> 终端可在证据充分时建议归为任务；标题无关且只因时间接近不得强合并。
3. **社交用途**：微信可以是工作协作，也可以是非工作插入；证据不足返回待确认。
4. **正常工具链**：短时间多次 `VS Code <-> Chrome <-> Terminal` 不得直接判定为非工作中断。
5. **视频/游戏/财务**：原有视频计量、游戏主动参与、投资分类及用户纠错决策保持不变。
6. **数据缺口**：睡眠、锁屏、暂停记录、跨午夜、墙钟回拨、采样间隙不构造不存在的连续性。
7. **历史兼容**：旧 metric/classification version 或缺少会话证据时，不能得出强趋势/强任务链结论。
8. **人工覆盖**：用户确认后延迟返回的 AI 不能覆盖；纠正/拆分/撤销操作断电恢复后仍一致。
9. **网络降级**：无 Key、总开关关、任务 AI 关、离线、月预算用完、超时、限流、坏 JSON 均不阻塞原始记录。
10. **额度幂等**：同一批证据重复刷新/重启不再次调用；预算记录异常时保守停止云端分析。
11. **隐私**：实际发送的请求中不得出现 URL、邮箱、路径、密钥等可识别模式；设置变化后排队的旧内容不得按原授权发出。
12. **注入与 UI 安全**：窗口标题中包含指令/富文本/SQL 字符时只作为数据处理，安全显示，不可影响命令执行。
13. **响应性能**：后台聚合与 AI 请求不阻塞采样/UI；大型历史数据下不产生无上限全表重复查询。
14. **发布兼容**：版本升级后旧设置和报告能读；回滚后原始数据仍可用。

测试必须使用模拟模型供应商，不消耗真实 API 配额。记录当前基线和更改后的结果，不以“测试应该通过”代替实际报告。
