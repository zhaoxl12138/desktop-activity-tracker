# DayLens 分阶段修改方案

日期：2026-10-20。状态：阶段 A、B 已实施；C/D 尚未实施。验收记录见 `../../reviews/2026-10-20-stage-a-result.md` 和 `../../reviews/2026-10-20-stage-b-result.md`。

依据：[项目重构评审](../../reviews/2026-10-20-project-refactoring-review.md)。

## 1．目标和交付边界

本次重构围绕三个结果：记录可信、纠错可控、界面易读。继续使用 PySide6 和现有唯一 SQLite 数据库；采用小步发布，每个阶段都能单独验收和回退。

第一版不迁移数据库表、不自动重分类历史记录、不改变参与阈值和播放器计时算法。先解决已复现的边界问题，避免把业务语义变化和界面调整混在一起。

后续涉及计量模型变化的阶段，先用固定样本进行新旧对照，明确差异和版本后再切换。API 日限额、批量上限和每月预算继续沿用现有设置。

## 2．发布顺序

| 版本阶段 | 主要内容 | 用户可见结果 | 出口条件 |
|---|---|---|---|
| A：可靠性修复 | 隐私过滤、状态覆盖、纠错目标、慢查询、安全升级 | 修改不反弹、所选记录不漂移、页面能持续刷新 | 六组复现转为正式回归，业务计量保持基线 |
| B：统一业务定义 | 分类注册表、数据路径、纠错工作台、时间说明 | 分类入口一致、知道规则为什么生效 | 规则/人工/AI贯穿采样、统计、报告 |
| C：首页及页面整理 | 紧凑顶部、响应式布局、卡片组件、导航归并 | 小窗口可用、主要数字清楚、无重复入口 | 长文本与真实 DPI 矩阵通过 |
| D：计量与性能重构 | 采样缺口、播放证据、历史缓存、模块拆分、报告截止时间 | 记录缺口可解释、历史浏览稳定 | 新旧对照完成，计量守恒和性能达标 |

A→B 为基础依赖；C 可在 B 的展示模型稳定后实施。D 中“代码拆分”和“改变计量策略”分别提交，先保持行为等价再切换算法。

## 3．阶段 A：先修复已验证的问题

### A1．统一 AI 隐私边界

增加一个统一的隐私过滤服务，所有出站事实通过同一入口：当前标题、最近标题上下文、日报事实和周月报压缩摘要。

- 标题进入最近上下文之前执行应用排除与关键词排除，再脱敏。
- 请求发送前，使用最新设置再次校验整个载荷；不允许调用方自行拼接绕过。
- 设置变化递增隐私版本，清理受影响的内存上下文和待发送任务。
- 排除规则变化时，尚未发送的旧版本任务重新构造载荷；已经进入网络发送的请求不能被视为可撤回。
- 周月报只继承当前允许使用的事实；无法确认旧摘要是否满足当前排除规则时，跳过该摘要或从允许的本地事实重建，不把旧摘要直接再次发送。
- 诊断日志只保留任务类型、过滤原因和本地指纹，不记录密钥或被排除的完整标题。

验收：被排除标题无论在当前项、前序上下文、设置变更前的队列还是压缩摘要中，都不能进入新的真实请求。使用假提供方记录最终载荷做断言，不靠界面文字推测。

### A2．人工决策与待确认数据采用一个写入入口

建立 `ClassificationStateService`，所有修改通过它提交：精确纠错、模式修改/启停/删除、待确认项接受/忽略和命中统计。

第一版继续使用现有 JSON 文件：

- 状态操作使用进程内共享锁和操作系统文件锁覆盖完整“读取→修改→保存”，而不只是原子替换文件。
- 每次命令从最新磁盘状态开始，保存后递增 revision；旧内存副本不能直接覆盖整个文件。
- 命中统计提交增量，只更新命中次数和最近命中时间，不写回分类、启用状态等决策字段。
- 确认和忽略保存为有界的已处理标记，防止迟到的同一 AI 结果重新创建该待确认项；明确重新评估时才开启新任务版本。
- 多文件操作通过一份小型恢复日志记录操作 ID、预期版本和完成状态。启动时幂等补完；所有读写入口使用同一锁协议。
- 保存成功后向界面反馈“已保存”；采集线程应用对应 revision 后反馈“已生效”。重载失败时显示待应用状态并可重试。

未来如果有必要把决策迁入现有 SQLite，另做兼容迁移设计和回退演练；A 版不增加表或第二个数据库。

验收：后台命中统计不能覆盖人工修改；忽略 A 后另一个任务写 B，A 不复活；中途失败可恢复；确认不会丢失现有会话计数。

### A3．纠错始终绑定同一条记录

- 实时样本增加仅用于界面绑定的稳定 sample ID。
- 用户选中时保存 ID 和样本副本；刷新按 ID 恢复选择。
- 所选项离开最近记录窗口时，将副本保留为“固定所选”，或明确提示已过期；不能自动换成新行。
- 操作名称使用“纠正所选记录”；没有选择时明确显示当前目标应用和标题。
- 对话框确认页展示应用、完整标题、原分类、新分类及作用范围。

验收：连续插入新样本、排序、滚动、打开弹窗期间刷新，都不能改变纠错目标。

### A4．修复快照刷新失效规则

把两个状态分开：

1. `context_revision`：页面、日期范围、配置或数据源变化时递增，用来丢弃真正无效的结果。
2. `refresh_pending`：查询进行时再次触发刷新，只合并为一次后续请求，不使当前查询失效。

当前上下文中的查询完成后先发布，再执行合并的后续查询。切换页面时可以拒绝发布；重新进入页面时立即刷新。上一份有效数据保留，同时显示加载中或更新失败及更新时间。

验收：连续三次查询都慢于计时器周期，页面仍获得完成结果；跨午夜、换日期、换数据源不会发布旧上下文数据。

### A5．安全退出和升级直接进入发布脚本

发布采用：构建 staging→隔离 smoke→请求 maintenance-exit→确认 clean 和进程结束→保存旧版→替换→启动验证。

- 正常发布路径不调用 `/f` 强杀；无法安全退出时停止替换。
- 留存本次旧版和构建标识；清理备份使用独立、可预览的清理命令。
- 验证启动、窗口、持续采样和数据库路径，失败后在安全退出新进程后恢复旧版程序文件。
- 第一版无 schema 变化，程序回退不需要回退数据库。以后如有迁移，须另行设计双向兼容窗口，不能直接恢复旧库覆盖新记录。

## 4．阶段 B：统一分类与计量展示定义

### B1．唯一分类注册表

`CategoryDefinition` 至少包含：稳定 ID、显示名、统计分组、显示顺序、颜色、默认计时策略、AI 是否允许返回、人工是否允许选择、旧 ID 别名。

由注册表派生：本地规则页选项、人工纠错选项、AI schema/prompt、采集器合法值、报表分组和界面颜色。注册表不在多个文件重新手写。

第一步保持已有 ID 和含义，投资理财继续独立；应用类型作为独立属性保存到展示模型中。较大的用途分类调整另行版本化，不自动改变历史记录。

自定义分类初期允许本地规则和人工选择，计时策略由受支持的策略列表选择；AI 只返回注册为 AI 可用的分类，不能凭名称自行创造分类。

### B2．固定决策优先级与结果格式

决策顺序：有效的人工精确纠错→有效的人工相似模式→明确本地规则→有效 AI 缓存→新 AI 结果→兜底。

结果统一为：最终分类、建议分类、来源、置信度、原因、模式 ID、决策 revision、生效时间和计时策略 ID。AI 高/中/低置信证据策略仍保留，不改成无条件接受 AI。

所有页面读取同一份结果，不能一个显示“待确认”，另一个只显示“浏览器”且没有说明。

### B3．分类管理工作台

将“规则管理”扩展为“分类管理”，页签为：

- 待确认：批量或逐条处理 AI 建议，展示来源与依据。
- 人工纠错：精确与相似两种范围，显示关联关系、启用状态、最近命中。
- 本地规则：沿用现有规则编辑能力。

一次纠正形成一个关联决策。停用时默认停用此次决策下的精确和相似部分，界面明确列出影响范围；高级操作可只停用相似扩展。用户主动创建的其他独立决策不受影响。撤销依据操作记录恢复前一版本。

实时监控只保留快捷纠错与跳转入口。已有独立精确纠错与模式按显式 pattern ID 关联；旧数据无法可靠关联时保持独立并说明，不凭脱敏标题猜测合并。

历史修正暂不纳入第一批开发；后续独立入口需先预览日期、记录数、分类前后时长与备份，再单独确认。

### B4．明确时间模型

采用下列定义，展示与报表共用：

- 主动参与 A：沿用当前参与判定得到的时间。
- 被动观看 P：满足播放策略确认条件的媒体时间。
- 有效活动 E＝A＋P。
- 已观测时间 O＝A＋P＋空闲 I。
- 未确认缺口 U 独立统计；记录覆盖区间＝O＋U，不包含应用尚未启动的整天时间。

阶段 B 只统一命名和展示。阶段 D 才引入新增缺口计量；旧数据没有缺口证据时显示“未知”，不能倒推出具体漏记秒数。

首页分类分布采用 E 为分母，圆环中心标“有效活动”，圆环各扇区与分类条对应。旁边状态条用明确文本显示“主动参与 A · 被动观看 P”；空闲与记录健康单独呈现。

分类条保留工作学习、娱乐、社交；投资存在时独立显示。剩余分类只显示最大项自身时长，底部提供“查看其余分类”，解释隐藏数量和时长。圆环可绘出全部分类，隐藏类别使用可查看详情的“未列出分类”中性扇区；不把它冒充末行分类，也不重新归一化已展示条形。

### B5．统一路径对象

启动时构造 `AppPaths`，之后显式传递，包含规范数据库、AI 状态目录、报告目录、恢复文件、日志目录和程序目录。

延续当前既有数据目录，首次解析后固定，AI 组件不能再一部分按 `get_data_dir()`、另一部分按数据库父目录各自推导。检测到分散状态时先报告来源和内容，不能静默新建另一套状态或数据库。

## 5．阶段 C：前端布局方案

### C1．导航和顶部

导航整理为：今日概览、统计、分类管理、报告中心、设置。实时监控作为可直达的诊断页面保留；统计中有软件/分类两个页签，报告中心有日/周/月三个页签。

首页顶部：标题和日期、一个有效活动主数、记录状态、暂停和报告操作。主动/被动解释使用小型摘要，不重复排列所有分类时间。诗词默认收起，可从设置恢复。

其他页面只显示页面标题和本页操作，不继续展示整块今日总览。首页顶部目标高度约 88～112 个逻辑像素；内容能换行，但不因窄窗口强制变成一块更高的仪表盘。

### C2．首页结构

宽窗口：

```text
┌ 导航 ┐  今日概览 / 日期     有效活动 / 状态     暂停 / 报告
│      │  ┌ 活动分布 ───────────┐ ┌ 工作节奏 ───────┐
│      │  │ 分类、时长、参与状态 │ │ 今日/7天/30天    │
│      │  └────────────────────┘ └─────────────────┘
│      │  ┌ 工作切换与关键片段 ─┐ ┌ 娱乐时间 ───────┐
│      │  │ 按内容展开，可看详情 │ └─────────────────┘
│      │  └────────────────────┘ ┌ 软件 Top5 ──────┐
└──────┘                         └─────────────────┘
```

布局按内容区可用逻辑宽度判断，不直接按物理分辨率猜测：

- 可用宽度≥1150：双栏，约 60%/40%，侧栏约176。
- 850～1149：紧凑双栏，侧栏可折叠到约64；正文卡片标题与操作允许分行。
- <850：单列，侧栏折叠；顺序为活动分布、工作节奏、娱乐时间、工作切换/片段、Top5。
- 内容超过高度时正常纵向滚动，首屏优先展示摘要和第一张核心卡片；不承诺在720高的屏幕内塞下全部模块。

卡片高度由内容和图表最低可读尺寸决定。宽屏可对齐上沿和栅格，不强行拉伸空片段卡去对齐右栏底边。长列表在详情页展开，首页保留摘要数量上限。

### C3．卡片细节

| 卡片 | 保留 | 调整 |
|---|---|---|
| 活动分布 | 分类条、投资独立、剩余最大分类 | 圆环与分类同口径；数值列按字体测量；隐藏分类可查看 |
| 工作节奏 | 今日累计、7/30天、日期范围 | 状态徽标简短，摘要格允许两行；时间单位一致 |
| 娱乐时间 | 7/30天、橙色、总量/日均/最高日 | 与工作卡共用摘要组件；最高日拆为日期和时长两行 |
| 工作切换 | 次数、累计、来源 | 默认称切换，可标为必要切换；不把所有离开工作视为干扰 |
| 关键片段 | 标题、应用、起止、参与时长 | 按内容高度，空状态收紧，保留用户现有时长筛选 |
| Top5 | 单行应用名与时长 | 保持简洁，点击进入完整统计 |

基础字号采用有限层级：正文约13～14、辅助约12、卡片标题16～18、主数值22～28个逻辑像素。9px 摘要不再作为常规字号。实际字号和色彩通过深浅主题及真实 DPI 截图确认。

复用 `PageHeader`、`CardHeader`、`MetricCell`、`DurationLabel`、`StatusBadge`、`EmptyState`、`ErrorState`。值不足空间时先换行/调整布局，再省略可展开的标题；核心时长不省略。

### C4．状态和文案

记录状态统一为：记录中、已暂停、正在保存、记录异常、待恢复；数据视图统一为：加载中、有数据、无记录、部分数据、读取失败。

无记录显示“尚无记录”，不显示一个看似完整的0分钟结论。失败保留上一份可用快照，并显示最后更新时间。分类口径提示放在需要比较的视图旁，不让整页长期充满“口径已变化”。

规则解释、来源和计量详情放入可展开详情；普通首页不展示大量技术名词和错误堆栈。

## 6．阶段 D：计量、性能和维护结构

### D1．采样缺口与播放器证据

正常采样抖动用单调时钟差值核算；较大间隔进入未确认缺口，阈值需通过回放样本和实际负载测试确定，不在设计阶段凭空指定。

播放器探测返回 `playing / paused / unknown`、证据来源和有效期。先用影子模式记录新旧判定差异，不改变当前用户时长；再依据“播放、暂停、静音、后台音乐、多播放器、锁屏、恢复”等场景确定正式策略。

未知不能无限当作播放，也不能立即全部算空闲。具体宽限和结束规则作为可解释策略单独验收。GPU 或网络探测如果以后增加，只作辅助证据，不能将加载、后台下载或普通GPU活动直接视为观看。

### D2．快照与查询优化

- 当天增量与已结束历史日分开；缓存键包含日期范围、计量版本、分类定义版本和数据 revision。
- 仅当统计结果实际变更时刷新相关展示模型；实时状态更新不触发整套30天重算。
- 软件与分类页查询转到后台；使用稳定行键更新模型，保留选择与滚动。
- 将 `trend / goals` 的旧消费者列清单，确认移除条件后停止旧模型计算，再删除兼容组件。
- 先记录同一数据集的耗时分位数、SQL次数、内存和采样延迟，再决定索引或预聚合；不为优化引入第二个库。

### D3．模块边界

建议形成以下职责，各自通过数据模型连接：

1. 采集：窗口、输入活动、播放证据。
2. 分类：注册表、本地规则、人工决策、AI建议。
3. 计量：状态机、经过时间、缺口、会话边界。
4. 持久化：会话、恢复、决策状态、路径。
5. 查询：日期范围聚合、统一展示模型、缓存。
6. 页面：布局、用户操作、渲染。
7. 报告：事实构建、确定性报告、AI附录、调度和导出。

先抽取纯函数/模型，再移动组件文件；每次拆分保持对外适配层，避免把一次大规模文件搬家与算法修改混成同一提交。

### D4．报告时间与版本

沿用每天23点自动智能汇总。报告标明“截至23:00”；自然日结束后可以仅更新确定性的统计部分，AI附录仍标明其独立截止时间，不自动触发第二次付费分析。

日报、周报、月报显示统计范围、数据更新时间、AI生成时间、待补/失败状态。历史日期范围取实际记录或用户设置；将8月13日的现有个人历史起点转为显式设置，不能删除该范围内旧数据，也不能继续用固定日期控制新算法行为。

## 7．验证、发布与回退要求

### 7.1 保护性基线

实施前保存代码基线、数据库一致性备份、AI状态文件、规则设置与报告目录清单。备份与程序目录分离，记录校验值。保留现有未提交改动，不与本次重构无关的功能混改。

数据库备份通过 SQLite 一致性备份机制执行，不在仍有 WAL 写入时只复制一个主文件。程序升级与数据库恢复是两个独立动作。

### 7.2 自动化与场景验收

- 现有939项测试作为基线；失败项必须确认原因，不能通过删除断言“修复”。
- A阶段所有复现转为正式测试，包括隐私边界、两个写入者、迟到结果、稳定选择与连续慢查询。
- 端到端验证：确认分类→下一次采样→会话切分→持久化→首页/软件/分类→日报。
- 时间守恒、跨午夜、休眠、暂停、异常退出恢复和数据源一致性。
- 深浅主题；1280×720、1600×900、1920×1080；100%、125%、150%系统缩放。按可用逻辑空间自适应，不能仅在 offscreen 下证明真实 DPI 无问题。
- 长标题、长时长、五分类、没有记录、部分记录、读失败、保存失败和AI不可用。
- 打包版启动、原数据库路径、持续采样、分类纠错、各页导航、正常退出、升级与程序回退。

### 7.3 交付物

每阶段交付：实现差异说明、回归与场景测试结果、同一组样本的前后对照、界面截图（有UI变化时）、发布版构建标识和回退位置。

## 8．建议的第一批实际开发范围

只实施阶段 A：

1. 隐私过滤覆盖完整出站载荷。
2. 分类状态统一写入与revision，解决模式反弹、忽略项复活及停用关联问题。
3. 固定所选记录与对话框目标。
4. 修复慢查询快照发布。
5. 安全升级进入正式脚本。

其余阶段先保持本设计约定，不同时切换布局和计量算法。A版稳定后再进入分类工作台和前端改版，便于判断每一次变化的影响。
